# 18 — Token-2022 transfer fee против номинального учёта

**Класс:** Extension confusion — протокол принимает Token-2022 актив и
начисляет обязательства по номиналу инструкции, не измеряя фактический
приход на свой счёт (и не ограничивая расширения mint'а).
**Файлы:** `programs/vuln18_token2022/`, `tests/18_token2022.test.ts`.
**Последствие:** эмитент mint'а с transfer fee «продаёт» протоколу токены
по цене без учёта комиссии — каждое пополнение выкачивает из SOL-казны
разницу, пока она не кончится.

## 1. Суть уязвимости

Token-2022 (SPL Token Extensions) массово внедряется с 2024 года и приносит
новую поверхность атак. Расширение **TransferFeeConfig** берёт процент с
каждого перевода: получатель получает `N * (1 - fee)`, разница «залипает»
в его аккаунте как withheld-остаток.

Протокол buy-back обменивает токены на SOL по курсу 1:1 и делает две
ошибки сразу:

1. `mint` не ограничен — подойдёт любой актив обеих token-программ;
2. выплата считается по номинальному `amount` из инструкции, а не по
   фактической дельте баланса казны.

Комиссию платит отправитель, а «получает» её... никто из протокола: на
балансе казны оседает меньше, чем протокол пообещал выплатить. Атакующий
сам эмитирует mint с комиссией 10% и продаёт его протоколу по кругу —
каждый цикл казна теряет 10% от суммы сделки.

## 2. Уязвимый код

```rust
token_interface::transfer_checked(
    CpiContext::new(..., TransferChecked {
        from: ctx.accounts.seller_ta.to_account_info(),
        mint: ctx.accounts.mint.to_account_info(),
        to: ctx.accounts.treasury_ta.to_account_info(),
        authority: ctx.accounts.seller.to_account_info(),
    }),
    amount,
    ctx.accounts.mint.decimals,
)?;

// БАГ #1: mint не сверён с whitelist'ом
// БАГ #2: payout — по НОМИНАЛУ, а не по фактической дельте казны
let new_vault = vault.lamports().checked_sub(amount)...;
**to.lamports.borrow_mut() = new_to;   // seller получает amount целиком
```

## 3. Как эксплуатируется

Тест `tests/18_token2022.test.ts`:

1. Честный сценарий: обычный SPL-mint без комиссий — продал 1_000_000
   единиц, получил ровно 1_000_000 лэмпортов, сходится.
2. Атакующий выпускает Token-2022 mint с
   `createInitializeTransferFeeConfigInstruction(..., 1000 bps, max)`,
   минтит себе 2_000_000 единиц.
3. Дважды вызывает `sell(1_000_000)`:
   - казна принимает по 900_000 единиц (100 000 — withheld fee),
   - атакующий получает по 1_000_000 лэмпортов за каждую продажу.
4. Итог: за 2_000_000 выплаченных лэмпортов казна получила токенов на
   1_800_000 — 200 000 лэмпортов украдены из SOL-казны.

```ts
await program.methods.sell(new BN(1_000_000))
  .accounts({
    vault, treasuryTa: attackerTreasuryTa, mint: feeMint, sellerTa: attackerTa,
    seller: attacker.publicKey, tokenProgram: TOKEN_2022_PROGRAM_ID,
    vaultAuthority: vault,
  })
  .signers([attacker]).rpc();
```

## 4. Результат атаки (проверяется тестом)

- Баланс атакующего вырос ровно на 2_000_000 лэмпортов (номинал обеих
  продаж).
- В токен-аккаунте казны: 1_800_000 единиц вместо 2_000_000.
- SOL-vault казны уменьшился ровно на 2_000_000 — по номиналу.
- Расхождение 200 000 лэмпортов — прямой убыток протокола с каждой пары
  циклов; повторение операции сливает казну целиком.

## 5. Реальные кейсы

- **Token-2022 как новая поверхность** — с 2024 по 2026 год доля T22-активов
  в mainnet постоянно растёт; аудиторские бюро (Neodyme, OtterSec, Sec3)
  публикуют серии находок, где протоколы, написанные под «старый» SPL
  Token, некорректно обрабатывают расширения (transfer fee, permanent
  delegate, interest-bearing).
- Прямых громких взломов именно transfer fee пока нет — класс остаётся
  «миной» для любых buy-back/ bridge/ vault-протоколов, которые считают
  по номиналу инструкции.

## 6. Исправление

```rust
// ПОСЛЕ: пиннем mint и учитываем фактическую дельту баланса казны
#[account(constraint = mint.key() == crate::AUTHORIZED_MINT @ Err18::WrongMint)]
pub mint: InterfaceAccount<'info, Mint>,

let before = ctx.accounts.treasury_ta.amount;
token_interface::transfer_checked(...)?;
ctx.accounts.treasury_ta.reload()?;
let received = ctx.accounts.treasury_ta.amount - before;
// платим за received, а не за amount
let payout = received.checked_mul(RATE).ok_or(Err18::Overflow)?;
```

Правила:

1. White-list расширений принимаемых mint'ов: transfer fee, permanent
   delegate, non-transferable — каждое расширение меняет семантику учёта.
2. Обязательства начисляйте по **фактической** дельте балансов
   (before/after + reload), никогда по аргументу инструкции.
3. Тестируйте протокол на T22-активах с расширениями — «обычный» SPL-тест
   этих классов багов не находит.
